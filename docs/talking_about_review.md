# 🗣️ [SKALA] Vector DB Talking About 복습 노트

> 진행 방식: 종합실습 들어가기 전에 개념교재 전체를 친구한테 처음부터 설명해주는 식으로 복습했다. 코드보다는 "왜 이게 필요하고, 다음 단계로 어떻게 이어지는지" 흐름을 말로 풀어보는 데 집중했다.

---

## 🗺️ 먼저 큰 그림부터 그려줬다

설명 시작하기 전에 오늘 내용 전체를 한 줄로 먼저 보여줬다. 이걸 먼저 깔아두니까 중간에 "이거 왜 하는 거야?"라는 질문이 거의 안 나왔다.

```
기초 RAG의 한계
   ↓
① 임베딩 잘 고르기  → 문장을 좌표로
② 잘 자르기        → Chunking, Parent-Child
③ 잘 저장하기      → FAISS에서 Qdrant로, 메타데이터
④ 잘 찾기          → Hybrid Search (Dense + BM25)
⑤ 한 번 더 고르기   → Re-ranking
⑥ 스스로 생각하기   → Agentic RAG
⑦ 숫자로 확인하기   → RAGAS
   ↓
그 다음은? → MEMO (아예 외워버리는 방식)
```

친구한테 "오늘 수업은 결국 RAG에서 **검색을 어떻게 더 정확하게 만드냐** 하나야. 단계마다 한 칸씩 업그레이드하는 거야"라고 말하고 시작했다.

---

## 1. 출발점: 기초 RAG가 뭐가 부족했나

교재 비유가 "책상 위에 책 5권만 올려두고 시험 보기"였는데 이걸 그대로 써먹었다. 질문이 오면 관련 있어 보이는 문서 5개만 골라서 LLM한테 주는 게 기초 RAG인데, 여기서 4가지 문제가 생긴다.

| 문제 | 친구한테 한 설명 |
|---|---|
| Context Window 제약 | 책이 두꺼우면 중요한 페이지가 통째로 빠진다 |
| Retrieval Noise | 엉뚱한 책이 섞이면 헷갈려서 오답 낸다 |
| Cross-Document 추론 | 여러 책을 왔다 갔다 해야 하는 문제는 못 푼다 |
| 키워드 의존 | 책에 있는 특정 단어 하나를 놓치면 아예 못 찾는다 |

그리고 "오늘 배우는 게 사실 이 4개를 하나씩 막는 방법이야"라고 연결해줬다. 이 표를 처음에 보여주고 나중에 다시 돌아오니까 흐름이 잘 잡혔다.

## 2. 임베딩: 문장을 지도 위 좌표로

> 친구: "임베딩이 정확히 뭐야?"
> 나: "문장의 뜻을 지도 위에 점으로 찍는 거야. 강아지랑 고양이는 가까이, 강아지랑 자동차는 멀리. 검색은 내 질문 점이랑 제일 가까운 점 찾기고."

이 비유 하나로 임베딩이랑 벡터 검색이 한 번에 설명됐다. 그다음 흐름은 이렇게 이어갔다.

**모델은 어떻게 발전했나**
Word2Vec(단어만 봄) → BERT(앞뒤 문맥 봄) → SBERT(문장을 점 하나로, 여기서 RAG가 시작) → BGE·E5(LLM 지능까지 흡수). 오늘 실습은 **BGE-M3**를 쓰는데 무료고 한국어를 잘해서다.

**모델은 어떻게 고르나**
MTEB라는 임베딩 올림픽 순위표가 있는데, 1등이 내 서비스 1등은 아니다. 교재 말대로 F1 레이싱카를 출퇴근용으로 쓰진 않으니까. 속도, 비용, 보안까지 같이 봐야 한다.

**거리는 어떻게 재나**
방법이 4개(Cosine, Dot, L2, L1) 있는데 실무는 거의 **Cosine**이다. 나침반처럼 방향만 보고 길이는 안 보니까 문장 길이가 달라도 비교가 된다.

**수백만 개를 어떻게 빨리 찾나**
전부 하나씩 비교하면 10초, **ANN**으로 대충 빠르게 찾으면 0.1초. 정확도는 1~5% 정도 손해 보는데 사람은 거의 못 느낀다. ANN 중 실무 표준이 **HNSW**고 비유가 고속도로 → 국도 → 골목길이다. 부산에서 서울 골목 찾아갈 때 처음부터 골목으로 안 가고 고속도로부터 타는 거라고 하니까 친구가 바로 이해했다.

**잘 찾았는지는 어떻게 아나**
**Recall@K**: 상위 K개 안에 정답이 있냐. 오늘 계속 쓰는 지표다.

## 3. Chunking: 결국 자르는 게 제일 중요했다

여기가 친구한테 제일 공들여서 설명한 부분이다.

**왜 자르나?** 100페이지를 LLM에 통째로 넣으면 토큰 초과, 비용 폭발, 응답 몇 분. 그래서 잘게 잘라서 필요한 조각만 준다.

**얼마나 자르나?**

| | 작게 자르면 | 크게 자르면 |
|---|---|---|
| 좋은 점 | 정확하게 찾음 | 맥락이 풍부함 |
| 나쁜 점 | 맥락이 끊김 | 의미가 흐려짐 |

교재 예시로 청크 크기만 바꿨는데 Recall@5가 **100토큰 0.52 → 500토큰 0.83 → 1000토큰 0.65**로 움직였다. 너무 작아도, 너무 커도 안 된다. 실무 기본값은 **300~500토큰 + 10% 오버랩**이고, 오버랩은 경계에서 문장이 뚝 끊기지 않게 살짝 겹쳐 자르는 거다.

> "모델 바꾸기 전에 청크부터 점검해라"

이게 Checkpoint에서 강조한 말인데 숫자로 보니까 확실히 납득이 됐다.

**자르는 방법 4가지**

| 전략 | 한 줄 | 언제 |
|---|---|---|
| Fixed | 길이로 무조건 자르기 | 빠르게 실험할 때 |
| Recursive | 문단 → 줄 → 문장 순으로 자연스럽게 | 처음 시작할 때 (기본) |
| Semantic | 뜻이 바뀌는 데서 자르기 | 최고 품질이 필요할 때 |
| **Parent-Child** | 작게 찾고 크게 전달 | **실무 배포** |

> 친구: "Parent-Child가 왜 두 마리 토끼야?"
> 나: "도서관에서 색인 카드(Child)로 위치를 정확히 찾고, 정작 읽을 땐 그 챕터 통째로(Parent) 꺼내주는 거야. 찾는 단계는 작아야 정확하고, 읽는 단계는 커야 이해가 되는데, 그 요구가 서로 반대니까 아예 둘로 나눠버린 거지."

대가는 저장 공간이 2배쯤 드는 것. 이 질문은 친구가 먼저 물어봐서 좋았다.

## 4. 저장: FAISS에서 Qdrant로

**메타데이터**는 청크에 다는 꼬리표다. 도서관 책에 선반 번호, 입고 날짜 붙이는 것처럼 페이지, 날짜, 카테고리를 같이 저장한다. 이게 있어야 "2024년 재무 문서에서만 찾아줘" 같은 **필터 검색**이 된다.

여기서 FAISS랑 Qdrant 차이가 자연스럽게 나온다.

| | FAISS | Qdrant |
|---|---|---|
| 비유 | 잠깐 펼쳐놓는 작업대 | 꼬리표까지 기록하는 정식 창고 |
| 메타데이터·필터 | ❌ | ✅ |
| 쓰는 곳 | 빠른 실험 | 실무 서비스 |

"FAISS는 벡터만 들고 있어서 이게 몇 페이지였는지 몰라. 그래서 필터가 필요하면 Qdrant로 간다"로 정리했다.

## 5. Hybrid Search: 의미 검색의 맹점 메우기

교재 예시를 그대로 보여줬다. "PostgreSQL 17.2 설치 오류 코드 42P01"을 의미 검색(Dense)으로 찾으면 "DB 기초 개념", "SQL 최적화" 같은 게 나온다. 분위기는 비슷한데 정작 17.2랑 42P01은 못 잡는다.

Dense가 약한 곳: **버전 번호, 에러 코드, 고유명사, 법령 번호, 수식, 새로 나온 단어.**

그래서 옛날 방식인 **BM25**를 다시 꺼낸다. 원리는 "희귀한 단어가 많이 나올수록 관련 있다." 학습이 필요 없어서 새 단어도 바로 처리한다.

| | Dense (의미) | BM25 (키워드) |
|---|---|---|
| 잘하는 것 | 동의어, 문맥 | 정확한 단어 매칭 |
| 못하는 것 | 번호, 코드 | 동의어, 문맥 |

표를 보면 서로 못하는 걸 정확히 채워준다. 그래서 둘을 합친다.

> 친구: "점수를 그냥 더하면 안 돼?"
> 나: "Dense 점수는 0~1이고 BM25는 0~수십이라 기준이 달라. 그래서 **RRF**는 점수 말고 **등수**만 보고 합쳐. 심사위원 두 명 채점 기준이 다르면 등수끼리 합산하는 거랑 같아."

두 검색 모두에서 상위권인 문서가 최종 1등이 된다. 법률, IT 문서, 의료, **금융 규정**처럼 번호랑 코드가 많은 도메인에서 특히 효과가 크다. 교재 판단 기준은 "Dense만으로 Recall@5가 0.7 미만이면 Hybrid부터."

## 6. Re-ranking: 서류 전형 다음 면접

Hybrid로 뽑은 후보도 순서가 완벽하진 않다. 그래서 한 번 더 고른다.

- **Hybrid = 서류 전형**: 수백만 개 중 50개를 빠르게 추림 (대충 봄)
- **Reranker = 대면 면접**: 질문이랑 문서를 한 쌍씩 마주 앉혀서 정밀 채점 (느림)

면접은 느리니까 전원 면접은 안 보고 서류 합격자 50명만 본다. 그래서 느려도 실용적이다.

그리고 조 발표 때 우리가 덧붙인 해석이 있다. **서류에서 떨어지면 면접 기회도 없다.** 앞단 검색이 정답을 50개 안에 못 넣으면 Reranker가 아무리 좋아도 소용없다. 그래서 결국 청크랑 Hybrid가 먼저다.

```
질문 → Hybrid(Top-50, 빠르게) → Reranker(정밀 채점) → 상위 5~10개 → LLM → 답변
```

## 7. Agentic RAG: 검색 1번으로 안 되는 질문

"2023년이랑 2024년 매출 비교해서 원인 분석해줘" 같은 질문은 한 번 검색으로는 못 푼다. 그래서 LLM이 스스로 판단하면서 여러 번 검색하는 게 Agentic RAG다.

| 패턴 | 친구한테 한 설명 |
|---|---|
| Query Decomposition | 큰 질문을 작은 질문으로 쪼개서 각각 찾기 (삼성 따로, LG 따로) |
| Query Rewriting | "저번에 말한 그 오류"를 검색 잘 되는 문장으로 바꾸기 |
| Self-RAG | 검색 필요한지, 결과가 맞는지, 답이 근거 있는지 스스로 채점 |
| Multi-hop | 첫 답을 힌트로 다음 질문 만들기 (저자 → 소속 → 연구비) |

Self-RAG는 LangGraph 수업 때 노드랑 조건 분기로 짰던 구조랑 같아서 연결해서 설명했다.

다만 무조건 Agentic이 좋은 건 아니다. FAQ 챗봇이나 고객 상담은 빠르고 싸야 하니까 기본 RAG, 리서치나 경쟁사 비교처럼 복잡한 건 Agentic. **복잡할수록 Agentic, 속도·비용이 중요하면 기본 RAG.**

**같이 짚은 것: 안전장치**
- 에이전트는 목표만 있으면 스스로 우회로를 찾는다 (교재의 샌드박스 탈출 사례, Reward Hacking)
- 문서 안에 "이렇게 답해라"를 몰래 심으면 LLM이 따라간다 (간접 프롬프트 인젝션)
- 문서 **5개만 심어도 90%** 확률로 답을 조작할 수 있다 (PoisonedRAG)
- 그래서 핵심 방어는 **검색된 내용과 사용자 지시를 프롬프트에서 분리**하는 것

이 부분에서 친구가 제일 놀랐다. 할 수 있는 것만큼 **못 하게 막을 것**도 설계해야 한다는 게 이 챕터 메시지였다.

**도구 연결은 MCP**: 에이전트랑 도구를 잇는 USB-C 같은 표준 규격.

## 8. RAGAS: 감이 아니라 숫자로

"좋아진 것 같다"가 아니라 "Faithfulness 0.6 → 0.9"라고 말하기 위한 도구다.

| 보는 쪽 | 지표 | 묻는 것 |
|---|---|---|
| 생성 | Faithfulness | 답이 문서에 근거했나? |
| 생성 | Answer Relevancy | 질문에 맞게 답했나? |
| 검색 | Context Recall | 필요한 문서를 다 찾았나? |
| 검색 | Context Precision | 좋은 문서가 위에 있나? |

활용 팁은 **점수가 낮은 쪽부터 고치기.** 검색 쪽이 낮으면 청크·검색 방식을, 생성 쪽이 낮으면 프롬프트·LLM을 손본다. 한계는 채점도 LLM이 해서 한국어에선 좀 부정확할 수 있다는 것.

## 9. MEMO: RAG 다음은 뭘까

마지막은 2026년 5월 논문 MEMO. 친구한테 제일 재밌게 설명한 부분이다.

> "RAG는 **사서**야. 손님 올 때마다 책장 가서 책 꺼내 읽어줘. MEMO는 **책을 다 외운 전문가**를 고용하는 거야."

**세 모델이 학원처럼 분업한다**

| 모델 | 학원 비유 | 하는 일 |
|---|---|---|
| Generator | 문제집 만드는 선생님 | 문서를 Q&A 문제집으로 변환 |
| Memory | 문제집 푼 학생 (작은 모델) | 공부해서 지식을 외움 |
| Executive | 상담 실장 (아무 LLM) | 질문 받아서 학생한테 물어보고 답 정리 |

상담 실장은 언제든 더 좋은 LLM으로 바꿀 수 있다 (Plug-and-play). 바꿨더니 추가 학습 없이 +26.73%.

**강점**
- 가짜 문서를 섞어도 RAG는 -6%, MEMO는 +0.5%. 지식이 머릿속에 있으니까 검색 단계 오염에 강하다
- 여러 문서를 엮는 문제를 학습 단계에서 미리 연습시킨다 (Step 5 교차 문서 합성, 빼면 성능 74% 폭락)

**약점**
- 학습비가 크다 (GPU로 90~180시간)
- 새 문서가 들어오면 다시 공부해야 한다. RAG는 그냥 꽂으면 끝인데
- (내가 덧붙인 것) 머릿속 기억이라 "몇 페이지에서 찾았어요" 같은 **출처**를 대기 어렵다

**내 결론**: MEMO가 RAG를 대체하기보다 역할을 나눌 것 같다. 잘 안 바뀌는 지식(규정, 매뉴얼)은 외우게 하고, 매일 바뀌는 지식(금리, 뉴스)이나 근거를 꼭 대야 하는 답은 RAG로. 특히 금융권은 "근거가 뭐냐"를 꼭 물어보니까 RAG가 쉽게 안 사라질 것 같다.

## ✅ 마무리: 친구랑 같이 정리한 오늘 핵심 5줄

1. **검색 품질은 자르는 데서 결정된다.** 모델 바꾸기 전에 청크부터. (0.52 → 0.83)
2. **Child로 찾고 Parent로 전달한다.** 정확함이랑 맥락을 둘 다 가져가는 방법.
3. **의미 검색이 놓친 번호·코드는 키워드 검색이 잡는다.** 합칠 땐 점수 말고 등수로 (RRF).
4. **서류 전형(Hybrid) 다음 면접(Reranker).** 근데 서류에서 떨어지면 면접도 없다.
5. **복잡하면 Agentic, 대신 막을 것도 설계.** 그리고 결과는 RAGAS로 숫자 확인.

## 💭 설명하면서 느낀 점

직접 설명해보니까 내가 진짜 이해한 부분이랑 대충 넘어간 부분이 확실히 갈렸다. Parent-Child나 Hybrid는 비유가 바로 나왔는데, HNSW 파라미터(M, ef)나 RAGAS 지표 4개 차이는 말로 하려니까 버벅였다. 그 부분은 실습하면서 다시 확인해야겠다.

그리고 교재가 내용을 따로따로 나열한 게 아니라 "기초 RAG의 한계 4개"를 하나씩 막아가는 구조였다는 걸 설명하면서 처음 알아챘다.

| 기초 RAG의 한계 | 오늘 배운 해결책 |
|---|---|
| Context Window 제약 | Chunking, Parent-Child |
| Retrieval Noise | Re-ranking, (더 나아가) MEMO |
| Cross-Document 추론 | Agentic RAG (Multi-hop), MEMO |
| 키워드 의존 | Hybrid Search (BM25 + RRF) |

처음에 깔아둔 표로 다시 돌아와서 이렇게 마무리하니까 친구도 나도 전체 흐름이 한 번에 정리됐다.
